----- Part 2: Secret -- sensitive DB credentials -----
----- the echo vs echo -n newline bug -----
$ echo "mypassword" | base64        # WRONG: adds trailing 

bXlwYXNzd29yZAo=
$ echo -n "mypassword" | base64     # CORRECT: no trailing newline
bXlwYXNzd29yZA==
(notice the first ends in "Ao=" -- that o= is the encoded 
 character)
$ cat secret.yaml
apiVersion: v1
kind: Secret
metadata:
  name: yatri-db-secret
  namespace: default
  labels:
    app: yatri-app

 production secrets need Sealed Secrets, External Secrets Operator, or a KMS-backed store like Vault.)

----- Part 5: Ingress -- one entry point for both services -----
NOTE: this cluster runs k3s via colima, which disables the default Traefik ingress controller.
ingress-nginx (the same controller the reference lab uses) was installed separately for this topic:
$ kubectl get pods -n ingress-nginx
NAME                                        READY   STATUS      RESTARTS   AGE
ingress-nginx-admission-create-kjfr6        0/1     Completed   0          8m7s
ingress-nginx-admission-patch-jmjh9         0/1     Completed   0          8m7s
ingress-nginx-controller-6d6c8bdd44-bt4pl   1/1     Running     0          8m7s

NOTE: the ingress.yaml here uses plain pathType: Prefix for /api and / (no regex/rewrite-target
annotation) because this backend ignores the request path entirely and always returns the same
config dump -- the routing concept (one host, two paths, two backend services) is identical either way.
$ cat ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: yatri-ingress
  namespace: default
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "false"
spec:
  ingressClassName: nginx
  rules:
    - host: yatri.local
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: yatri-backend-service
                port:
                  number: 80
          - path: /
            pathType: Prefix
            backend:
              service:
                name: yatri-frontend-service
                port:
                  number: 80
$ kubectl apply -f ingress.yaml
ingress.networking.k8s.io/yatri-ingress created
$ kubectl get ingress yatri-ingress
NAME            CLASS   HOSTS         ADDRESS   PORTS   AGE
yatri-ingress   nginx   yatri.local             80      3s

----- Part 7: What happens when you update a ConfigMap while pods are already running? -----
$ kubectl patch configmap yatri-app-config --type merge -p "{\"data\":{\"ENVIRONMENT\":\"staging\"}}"
configmap/yatri-app-config patched
$ kubectl exec deployment/yatri-backend -- env | grep ENVIRONMENT      # does the RUNNING pod see it?

(unchanged -- env vars are injected once at container start; editing the ConfigMap does not
 live-reload them into an already-running process)
